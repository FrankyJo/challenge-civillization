## Independent review

A `reviewer` subagent (Sonnet) reviewed the diff and ran all three integration suites. It reported 1 high, 4 medium and 4 low findings.

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | High | The reset guard could be bypassed with `?host=`/`?hostaddr=` (node-postgres query overrides). | The guard rejects any query parameter and checks the host resolved by `pg-connection-string`; unit tests cover `host`, `hostaddr`, `service` and non-loopback. |
| 2 | Medium | One failing world aborted the reconciler cycle. | Per-world try/catch with a failure count; a test covers a broken world next to a healthy one, plus the documented rebuild. |
| 3 | Medium | The relay held a transaction and locks during publish, and `queue.add` could hang. | Short leasing claim statement (`SKIP LOCKED`), publish outside any transaction with a 5 s timeout, lease expiry for crashed relays; tests cover timeout and lease. |
| 4 | Medium | Poison jobs were retried 8 times; contention beyond 3 attempts was untested. | `UnrecoverableError` for unknown or malformed jobs (tested); default attempts raised to 5, with rationale documented; 8-writer test added. |
| 5 | Medium | Every unique violation was mapped to `IdempotencyConflictError`. | Only `command_log_command_id_key` maps to it; any other violation is a `LedgerIntegrityError`. |
| 6 | Low | `world_state` was unguarded at the DB level; role separation was undocumented. | Forward-only and no-delete/truncate trigger (tested). Role requirements are documented; provisioning is Phase 24 (risk below). |
| 7 | Low | A default partition could trap rows. | The default partition was removed, with a test. |
| 8 | Low | The digest was too strict and rejection key pinning undocumented. | `correlationId` is excluded from the digest; pinning of state-dependent rejections is documented. |
| 9 | Low | Test gaps. | Covered by the tests added for 1–7. Redis being *unavailable* during relay is covered at unit level by the publish timeout, not by a live outage test. |

After the fixes: `db` 39/39, `simulation` 5/5, `worker` 8/8, and the full gate is green.

## Compatibility, rollout, and rollback

- **Migration order:** `0002` then `0003`. Both only create new objects: no lock on existing data and no rewrite. Phase 02 had no persisted world data, so there is nothing to backfill.
- **Rollout:** deploy migrations, then the worker (relay, consumer and reconciler start automatically), then the simulation. The API is unchanged.
- **Rollback:**
  - `0003 down` drops the projection and its cursors (rebuildable).
  - `0002 down` refuses once any world exists (SQLSTATE 55000), because the ledger is never dropped by a migration. Production rolls forward.
  - Code rollback to Phase 02 leaves the new tables unused and harmless.
- **Projection rebuild/reconciliation:** delete the projection rows and the consumer's offsets; the reconciler rebuilds within one interval (`docs/PERSISTENCE.md`).
- **Development reset:** `pnpm db:reset`, refused unless all hold: not production, explicit flag, loopback host, no query parameters.
